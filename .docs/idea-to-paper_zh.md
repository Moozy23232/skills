# Idea to Paper：从想法到论文

[English](idea-to-paper.md)

`idea-to-paper` 帮你把一个研究方向、初步想法或已有项目，逐步推进成一篇“每个重要结论都能找到文献或实验依据”的论文。

它不是一键生成论文的工具。更合适的理解是：它是一位科研搭档，帮你判断什么值得验证、现有证据到底说明了什么，以及下一步应该做什么。

## 它能帮你做什么

下面这些情况都适合使用：

- 只有一个大方向，还没有形成具体研究问题；
- 已经有了研究想法，想知道相近工作是否已经做过；
- 需要把模糊假设变成可以被实验推翻的具体方案；
- 隔了一段时间重新打开科研仓库，不清楚项目推进到哪里；
- 已经有实验结果，需要判断应该继续、转向还是停止；
- 准备写论文或修改论文，希望每个重要结论都能和真实证据对应起来。

你不需要从第一步开始，也不必提前准备完整材料。一句话、几篇论文、零散笔记、代码仓库、实验日志、图片或论文草稿都可以作为起点。

## 可以直接这样开始

从宽泛方向寻找问题：

```text
请使用 $idea-to-paper。我想研究如何降低长上下文推理中的 KV-cache
显存占用。先帮我梳理相关工作，再找几个能在两张 GPU 上验证的研究问题。
```

检验一个初步想法：

```text
请使用 $idea-to-paper 检查这个想法：<你的想法>。找出最接近的已有工作、
最强的替代解释，以及一个能尽快证明这个想法不成立的最小实验。
```

接手已有项目：

```text
请使用 $idea-to-paper 查看这个仓库。结合现有笔记、代码和实验产物，
总结目前真正得到的结论、还缺什么证据，以及我下一步需要做的决定。
```

从实验结果走向论文：

```text
请使用 $idea-to-paper 检查这些实验结果和论文草稿。告诉我哪些结论已经
有证据，哪些还要补实验，哪些应该缩小范围或删除。
```

如果已经知道，最好同时告诉它：

- 你关心的问题或现象；
- 已经看过的论文、方法和对比基线（baseline）；
- 能使用的数据、算力、时间和专业能力；
- 目标会议、期刊或截止日期；
- 不能改变的约束。

这些信息不完整也没关系。它会优先追问真正影响研究方向、成本和可信度的决定，而不是要求你先写一份完整需求文档。

## 实际会怎样推进

`idea-to-paper` 会先判断项目现在处于什么位置，不会为了“走流程”而把已经完成的工作重做一遍。

1. **把问题说清楚。** 明确研究场景、预期贡献、关键假设，以及出现什么结果就说明想法不成立。
2. **检查相近工作。** 搜索最相关的论文，区分真正的贡献差异和换名字、换实现之类的表面差异。
3. **做阶段性判断。** 给出 `GO`、`PIVOT`、`HOLD` 或 `NO-GO` 建议，并说明理由和仍然存在的不确定性。
4. **先验证最便宜的风险。** 在投入大规模实验之前，先设计能暴露关键问题的小测试。
5. **积累可靠证据。** 保存实验方案、运行记录、失败结果和解释边界，让结果可以复现，也能公平比较。
6. **根据证据写论文。** 先让论文中的重要结论与文献或实验对应，再润色表达。

推进过程中，你应该始终能看到：检查过哪些证据、哪些地方还不确定，以及满足什么条件才能进入下一步。

四种建议分别表示：

- `GO`：现有依据足以支持进入下一次验证；
- `PIVOT`：核心方向仍有价值，但结论或方法需要调整；
- `HOLD`：必须先补齐某项证据、权限或资源；
- `NO-GO`：已有工作、错误假设或不可行性已经推翻核心想法。

## 通常会得到什么

| 你的需求 | 典型产出 |
|---|---|
| 探索一个方向 | 术语地图、相关研究分组和候选研究问题 |
| 检查一个研究想法 | 与最相近工作的对比、可行性风险，以及 `GO`/`PIVOT`/`HOLD`/`NO-GO` 建议 |
| 制订研究方案 | 可证伪假设、baseline、指标、成功阈值、分阶段实验、风险和停止条件 |
| 恢复已有项目 | 经实际产物核对的项目状态、矛盾或缺失项、当前证据检查点和下一步行动 |
| 分析实验 | 结合实验协议的结果解释、被推翻的假设、后续实验和结论取舍 |
| 构建论文 | 结论与证据的对照表、写作顺序、缺失证据清单和按优先级整理的审稿问题 |

所有建议都以实际检查过的来源和产物为依据和范围。`GO` 表示“值得进入下一次验证”，不等于已经证明新颖，更不等于保证发表。

## 用通俗的话理解实验阶段

`idea-to-paper` 会逐步提高证据强度，避免把“代码能跑”误当成“研究结论成立”。

| 阶段 | 它回答的问题 |
|---|---|
| Spike（技术探路） | 风险最高的关键技术，最基本的可行性存在吗？ |
| Smoke test（链路检查） | 完整链路能跑通，并且能产出可读取的结果吗？ |
| Pilot（预实验） | 初步信号是否值得投入一次规范实验？ |
| Formal experiment（正式实验） | 在固定、公平、可复现的方案下，核心结论还能成立吗？ |
| Ablation / robustness（消融与稳健性实验） | 为什么有效？换条件以后，边界在哪里？ |

只要证据不支持继续，你可以随时停止、修改想法，或者回到前面的阶段。

## 让长期项目不再失忆

如果只做一次简短分析，不需要建立任何额外目录。研究需要跨越多次对话时，可以这样说：

```text
请使用 $idea-to-paper 在这个仓库中建立可持续的研究记录。
写入之前，先告诉我会创建哪些内容。
```

得到你的同意后，`idea-to-paper` 可以在项目的 `docs/research/` 中建立：

- 研究地图和项目概览；
- 已做决定、待解决问题和当前计划；
- 实验协议、运行记录和实验索引；
- 论文结论与证据的对应表。

这套结构完全可选。它只创建缺失文件，所有内容都留在你指定的项目内；如果仓库已经有同类记录方式，就直接复用，不再建立一套平行系统。

### 为什么 skill 里会有一个初始化脚本？

这个脚本只是为了稳定地创建同一套研究目录和空白文档，避免每次对话都临时手工拼一遍。通常不需要你亲自运行：当你要求建立长期研究记录时，skill 会先展示预览，再在你同意后使用它。

脚本本身不会调研文献、运行实验或写论文。

## 可选的 `grill-me` 深度追问

`idea-to-paper` 可以独立完成整个流程。如果方案中仍有几个会影响方向的重要选择，它可能建议使用原版 `grill-me` 做一次聚焦的深度追问。

- 是否使用由你决定；
- 如果没有安装，你可以拒绝安装并继续使用内置追问；
- 已有安装不会被修改或重装；
- 追问只负责澄清决定，不会修改文件、运行实验或接管研究流程。

这个选项最适合在正式确定实验方案之前使用。它不能替代文献调研、证据判断或论文审查。

## 它不会假装做到什么

- 一次搜索没有找到相同工作，不等于研究想法已经被证明新颖；
- 代码链路跑通，不等于科研结论成立；
- 单次成功实验，不会自动被当成可靠结论；
- 缺失的引用、实验和数字，不会用“看起来合理”的内容补出来；
- 失败实验和负结果不会从研究记录中消失；
- 大规模或高成本实验会先说明范围与成本，再征得你的确认；
- 所有项目写入都限制在你明确指定的科研仓库中。

如果只是润色普通文章、总结单篇论文，或者处理与科研项目无关的日常编码，更适合使用范围更窄的工具。
